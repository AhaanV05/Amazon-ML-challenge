Entity Resolution Game Plan

Link every Source 1 business to its noisy copies in Sources 2 and 3, scored by per-entity F0.5. The plan: high-recall blocking, a feature-rich pairwise model, context features that see the whole candidate graph, and a decoder that picks, for each entity, the answer set with the highest expected score.

Reading the metric

Where the points are

  1. Every Source 1 entity is worth exactly one point.F0.5 is computed per entity and averaged. An entity with seven true matches counts the same as a singleton. We optimize decisions per entity, not per pair.
  2. Singletons are free points or instant zeros.An empty list on a true singleton scores 1.0; predicting anything scores 0.0. An empty list on an entity that does have matches also scores 0.0. The empty-or-not decision is its own problem.
  3. Precision counts double, but not blindly.Once the first match is at 0.9, a second one needs about 0.66 to be worth adding. Yet with three candidates at 0.4 each, predicting all three beats predicting none. A single global threshold gets both cases wrong.
  4. Blocking sets the ceiling, and its size is judged.A match that never becomes a candidate can never be predicted, and since 26 Sep the organizers rank smaller candidate sets higher at the final review. Retrieve wide inside the pipeline, then cut with a learned filter to the smallest set that keeps validation F0.5.
  5. France is the hidden exam.It has zero training rows but counts like every other test entity. Every feature must work for a country the model never saw, and leave-one-country-out validation is how we prove it.
Architecture

Eight stages, two output files

  1. NormalizeClean text, split legal form, parse address parts
  2. RetrieveThree sparse TF-IDF routes per country: name@place, address, joint; never exported
  3. FilterCheap learned filter cuts to a small adaptive set, possibly emptycandidate_pairs.tsv
  4. Pair featuresName, address, commonness and provenance signals, grown by family
  5. Stage-1 modelsLightGBM (as built; CatBoost dropped), cross-encoder scores as features
  6. Context featuresRanks, competition, cross-source triangles
  7. Stage-2 modelGBDT on everything, calibrated
  8. DecodeOne S1 per record, then expected-F0.5 subset per entitymatching_results.tsv

The candidate file is the filter's output, which is exactly what stages 4 to 8 score. Every predicted match is therefore a candidate by construction, which the validator checks. The retrieval union stays internal, because the organizers define the candidate file as the last filtering stage.

Stage 01

Normalize: two views of every field

Keep a lightly cleaned view (lowercase, whitespace fixed) and a fully normalized view of each field. Compute similarities on both and let the model decide which one to trust. Aggressive normalization helps on seen noise and can hurt on France, and keeping both views protects us.

Business name

  • Unicode NFKD, strip accents with the standard library (é→e, ç→c). Lowercase, unify punctuation, &→and.
  • Split the legal form from the core name: inc, llc, corp, co, ltd, lp, llp · pvt, private, limited, opc · sarl, sas, sasu, sa, eurl, snc, sci, cie, ets, sté. Output the core name, a canonical legal form, and a flag for its presence.
  • Trade names: split on dba, d/b/a, t/a, trading as, aka and parentheses. Name similarity is the max over the alternatives.
  • Transliteration skeleton: sri/shri/shree→sri, ph→f, ee→i, oo→u, w→v, drop inner vowels, collapse doubled letters. "Aggarwal" and "Agarwal" become the same key.

Business address

  • Postcode: last 6-digit (India, join "560 001"), or 5-digit (US ZIP, French code postal). ZIP+4 reduces to 5 digits.
  • Premise numbers: all other numbers, including 12bis, #14, "plot no 45", "no. 7", kept as a set.
  • Landmarks: near, nr, opp, opposite, behind, beside, next to, en face de … up to the next comma. Move them to their own field and out of the main address.
  • Units (suite, apt, floor, flat) go to their own field. The last two or three comma segments form the city/state tail.

Mine the abbreviation table from the training pairs

The noise was generated by some process, and training pairs show its substitution table. For each true pair, align tokens and count substitutions where one token is a prefix or subsequence of the other (rd↔road, pvt↔private, intl↔international). Keep the frequent ones as the canonical map, plus a small hand seed list. Mine inside each training fold: mining on every training pair leaks the held-out entities into validation. Resolve "St" by position: before a proper name it is Saint (Rue St Denis), after a street name it is Street (Main St). For France, apply the same prefix rule to unlabeled test records: short tokens that are prefixes of frequent longer tokens in the same country (av→avenue, bd→boulevard). That uses only provided data.

Stages 02 – 03

Blocking: retrieve wide, filter small

Since 26 Sep, candidate-set size counts in the final ranking: the organizers review candidate_pairs.tsv and the code behind it, and rank smaller sets per S1 entity higher. Blocking is therefore two stages. Retrieval casts a wide net (≥ 99.5% pair recall) that is never exported. A learned filter then cuts each entity's list to the smallest set that keeps validation F0.5, and that filtered set is the candidate file. Block within country if the hour-zero check allows it, and query S2 and S3 separately.

The learned filter, the last blocking stage

  • Inputs are retrieval-time signals only: which routes hit, rank and score in each, reverse rank, exact-key hits, plus a few cheap checks (postcode equal, a shared premise number, name TF-IDF cosine). A small LightGBM trained inside the training folds predicts P(match).
  • Keep rule per pair: filter probability ≥ τ, the S2/S3 record is among its own top r anchors, and at most Kmax per entity and source. Because a record belongs to at most one S1 entity, r = 1–3 cuts chains hard. An entity may end with no candidates, which is a free and correct call for most singletons.
  • Choose τ, r and Kmax on a curve. Run the full downstream pipeline out of fold and plot validation macro F0.5 against mean candidates per S1 entity. Take the knee, the smallest sets before F0.5 starts to drop, and put the curve in the methodology.
  • Keep the line between blocking and matching clear. The filter uses only cheap signals and is tuned for recall at small size; everything from pair features onward is the matching model. A filter that effectively makes the final decision would turn the candidate file into the answers, and reviewers read the code.

Measure what the reviewers will measure

  • On every run: mean, median, p95 and max candidates per S1 entity; share of entities with no candidates; pair recall after the filter; reduction ratio against all same-country pairs; each route's unique recall contribution.
  • Keep every route sub-quadratic: hash keys, inverted indexes or approximate nearest neighbours, never a dense N×M similarity matrix or all pairs inside a block. Cap oversized key blocks, such as a very common postcode. State each route's complexity in the methodology, since the organizers frame blocking as a billions-of-records problem.
  • Track the oracle ceiling: the macro F0.5 a perfect classifier would reach on these candidates. For an entity with m true matches of which c were retrieved, it is 1.25c / (c + 0.25m), and 1 for a singleton. It prices blocking misses in the metric's own units.
  • Why B, C and F exist: a chain like Starbucks can appear hundreds of times in S1. Name-only blocking returns an arbitrary 20 of them.
  • Records with identical text under several ids: compute features once, then expand back to every id. The metric expects all of them.

Stages 05 – 07

Models: a ranker, a reader and a referee

Stage 1 · Pairwise GBDT core

As built: LightGBM alone for the filter and both stages, natural class balance, probabilities fed straight to the decoder; the rest of this paragraph is the original plan. CatBoost binary classifier on all candidate pairs (depth 5–8, learning rate 0.03–0.1, up to about 1,500 iterations with early stopping), with LightGBM as a second model for diversity. Add monotone constraints on the main similarities so higher similarity never lowers the match probability; this keeps the model sane on France. Keep the natural class balance for the final probabilities, because the decoder needs them calibrated. Per-entity weighting (equal total weight per S1 entity) is worth one experiment, with recalibration afterwards. After the first model, mine its confident false positives inside the training folds and retrain once.

Cross-encoder Colab A100/H100

Our weakest signal is India names (AUC 0.72–0.75, about 9% in Indic scripts), where a multilingual transformer reads what string metrics cannot. We fine-tune xlm-roberta-base (MIT, 278M) on raw lowercased name | address pairs in their original scripts, one epoch, bf16. It trains on a separate 10% of training entities, disjoint from the LightGBM work set, so its scores on the work set are out-of-sample without k-fold training. It then scores every kept work-set and test pair, and ce_logit becomes a feature in both LightGBM stages. It runs from colab/cross_encoder.ipynb through the Colab extension in VS Code, with data passed through Google Drive. In v3, BAAI/bge-reranker-v2-m3 (Apache-2.0, ~568M) trains on the same entities in the background on the GPU and rescores only the pairs the base model is unsure about (probability 0.02–0.98) as a second feature. candidate_pairs.tsv is unchanged: the cross-encoder scores exactly the filtered set.

Stage 2 · Context features core

This is where the clustering idea earns its place. Built from stage-1 out-of-fold probabilities:

  • Entity view (for pair e, x): rank of x in e's list, gap to e's best, e's top-1 and top-2 probabilities, count of e's candidates above 0.5 and 0.8.
  • Competition: x's best probability with any other S1 entity, whether e is x's best (mutual best), and the margin.
  • Triangles: train the same pipeline on S2↔S3 pairs (positives are two records of the same S1). Feature: max over e's S3 candidates y of min(p(e,y), p(x,y)). If x's S3 twin is confidently e's, x probably is too.
  • Same-source duplicates: x's similarity to e's other confident candidates from its own source.

A second GBDT trains on pair features plus context features, then isotonic calibration on its out-of-fold predictions.

LLM referee optional, Day 3

Only for the uncertain band (stage-2 probability 0.3–0.7) and only if validation shows a gain. Use Qwen/Qwen3-Reranker-4B or Qwen3-4B (both Apache-2.0), scoring "same business? yes/no" and using the yes-probability as a feature. Llama and Gemma are out: their licenses aren't MIT or Apache.

Parameter budget. Until the organizers say otherwise, treat the 8B limit as a total across every neural model in the final system. Qwen3-8B has 8.2B parameters and fails on its own, and a 7B LLM plus a 0.57B reranker plus a 0.28B embedder also goes over. Keep a manifest of exact parameter counts and licenses taken from each model card. Quantization lowers memory, not parameter count.

Stage 08

Decoding: where F0.5 is won

  1. Conflict resolution. If the hour-zero check confirms it, each S2/S3 record keeps only its highest-probability S1 entity. Alternatively, run a greedy global assignment: sort all pairs by probability and accept a pair only while its record is still free.
  2. Expected-F0.5 subset per entity. Sort an entity's candidates by probability. For k = 0 … K compute the expected score of predicting the top k, where k = 0 is the empty list. Pick the best k. The positives among the top k and among the rest follow Poisson-binomial distributions, so this is exact and fast.
  3. Blocking misses. Fold the expected number of missed matches (from validation recall after the filter) into the "rest" distribution.
  4. Singleton gate (compare). An entity-level model for P(has any match) from top probabilities, counts and name commonness. Keep it only if it beats what the decoder already implies.

Expected F0.5 assuming independent, calibrated probabilities; verified by brute-force enumeration. With a first match at 0.95 / 0.90 / 0.80 / 0.70, a second is worth adding only above 0.69 / 0.66 / 0.59 / 0.52.

def poisson_binomial(ps):
    dist = [1.0]
    for p in ps:
        nxt = [0.0] * (len(dist) + 1)
        for i, d in enumerate(dist):
            nxt[i] += d * (1 - p); nxt[i + 1] += d * p
        dist = nxt
    return dist

def f05(tp, n_true, k):
    if n_true == 0 and k == 0: return 1.0
    if k == 0 or tp == 0: return 0.0
    return 1.25 * tp / (0.25 * n_true + k)

def best_subset(cands):          # cands: [(entity_id, calibrated_p), ...]
    cands = sorted(cands, key=lambda c: -c[1])
    ps = [p for _, p in cands]
    def score(k):
        top, rest = poisson_binomial(ps[:k]), poisson_binomial(ps[k:])
        return sum(top[a] * rest[b] * f05(a, a + b, k)
                   for a in range(len(top)) for b in range(len(rest)))
    k = max(range(len(ps) + 1), key=score)
    return [eid for eid, _ in cands[:k]]

Drop candidates below about 0.02 first; most entities are then left with fewer than six, and the cubic cost disappears. Keep a tuned two-threshold decoder as the baseline and ship whichever validates better.

Unseen country

France: generalize, then verify

  • Country-neutral features only. Generic postcode and number handling, char n-grams, multilingual embeddings. "Same country" is the only country feature.
  • Per-country IDF fitted on all records, test included. "rue", "sarl" and "avenue" become low-weight automatically, with no hand rules needed.
  • A French seed list for legal forms, street types (rue, av, bd, pl, ch, imp, quai, rte, fbg, allée), saint/sainte, and articles as stopwords (de, du, des, la, le, l', d'). Split elisions: l'atelier → atelier.
  • Leave-one-country-out validation. Train on US and score India, then the reverse. Features that collapse under the shift get dropped or constrained. This is our only offline proxy for France.
  • Sanity checks on test France. Predicted singleton rate and candidate counts should resemble US and India. If France predicts 90% singletons, something upstream is broken, most likely the country label.
  • A leaderboard probe. Two submissions that differ only in France predictions measure the France effect directly.
  • What happened (27 Sep). France scored ~0.93 while India/US matched validation at ~0.985. Every model variant agreed on 96% of French predictions, so the loss was upstream: full French candidate lists (57% at the cap) dropped alias, domain and initials records, and the matcher rejected suffix copies because of the word itself.
    • The sibling bridge and the suffix/near-copy rules lifted France to ~0.942.
    • A same-address word-swap rule, true 90–94% in India/US, lost 0.0029 in France and was dropped.
Trust the local score

Validation protocol

  • Metric first. Implement exact macro F0.5 with singletons and unit-test it on the PDF example (0.714).
  • Splits. Group each S1 entity with its true matches so an identity never straddles folds. Day 1: one grouped development split plus a small untouched audit split, stratified by country, singleton status and match count. From Day 2: grouped out-of-fold predictions for stacking (5 folds for the GBDT stages, 3 if a neural stage is too slow). The audit split is for finalists only. Run blocking on the full training gallery so every fold keeps realistic distractors, and add leave-one-country-out on top.
  • No held-out records in training pairs. When fitting a fold, drop candidate pairs whose S2/S3 record belongs to a held-out entity.
  • Don't force missed positives into training. Positives that blocking missed are the least similar ones. Adding them teaches the model to accept weak pairs it will never see at test time. Log them as blocking failures instead.
  • Out-of-fold discipline. Every feature built from model predictions (context features, cross-encoder score, calibration) uses out-of-fold values on train and the full-train model on test.
  • One scorecard per experiment. experiments.csv with commit hash, pair recall and oracle ceiling, macro F0.5 overall / US / India / non-singletons, singleton false-positive rate, leave-one-country-out F0.5, candidates p50/p95, runtime, peak memory, and leaderboard score when submitted.
  • Sanity floor. An all-empty prediction scores exactly the singleton share. Every model must beat it on both the singleton and non-singleton slices.
  • Compare finalists with a paired bootstrap over S1 entities. A gain inside the noise band isn't worth extra complexity.
  • Public leaderboard is a sample. When it disagrees with a 5-fold score, believe the folds.

Compute

  • Laptop RTX 4060/5060 (8 GB): TF-IDF, RapidFuzz, LightGBM, embedding inference, small cross-encoder runs with short sequences.
  • Colab A100/H100 (team subscription): cross-encoder training and scoring of every kept pair; later a dense retrieval route or the 4B reranker.
  • CPU-only fallback: the lexical + GBDT system alone is competitive and must always be able to ship.

Team of four

  • Teammate 1 · Validation and shipping: scorer, frozen split ids, transfer tests, experiment log, submissions (designated uploader), methodology.
  • Teammate 2 · Normalization and blocking: text views, the six blockers, recall and oracle reports, candidate provenance.
  • Teammate 3 · Features, GBDT and decoding: pair and context features, stages 1 and 2, calibration, expected-F0.5 decoder.
  • Teammate 4 · Neural: embeddings, cross-encoder, 4B reranker, GPU profiling, parameter and license manifest.

Everyone reads and writes one pair table: source1_entity_id, candidate_entity_id, fold_id, route provenance, and the label on training rows.

Don't lose on paperwork

Compliance and package checklist

  • No external APIs, geocoding, business registries or internet data. Pretrained open models are fine, since the rules explicitly limit their license and size. Hand-written abbreviation lists are code, not lookups; state them openly in the methodology.
  • Every model is MIT or Apache-2.0, and the neural models together stay under 8B parameters. Keep a manifest of exact counts and licenses.
  • Exactly one row per test S1 entity, no duplicate rows, no duplicate ids in a list, S2/S3 ids only, all ids exist in test, empty string for singletons.
  • Every matched id also appears in candidate_pairs.tsv, which is the exact set the model scored.
  • candidate_pairs.tsv comes from the same run as the final matching_results.tsv. The methodology reports its size distribution, reduction ratio, recall ceiling, the size-versus-F0.5 curve, and each route's complexity.
  • utils/validate_submission.py prints PASS, run automatically at the end of the pipeline.
  • Zip layout: output/ (both TSVs), code/business_entity_resolution/ (src/, README.md, pinned requirements.txt), Documentation_template.md.
  • One command reproduces both outputs from the data. Seeds fixed, runtimes and hardware listed in the README.
  • Methodology covers approach, blocking strategy, model architecture and feature engineering. The guidelines mention a 1–2 page write-up and the problem statement a template with no page limit, so fill the template and open it with a one-page summary.
  • Git history with a tag per submission. One login per participant, desktop or laptop only.
What goes wrong

Risks and mitigations

RiskMitigation
Chains and franchises (same name, many addresses)Address-aware blockers, reverse blocking, name-commonness feature
Shared addresses (malls, towers)Address-commonness feature, so the name decides
Near-duplicate but distinct S1 entitiesOne-S1-per-record conflict resolution, margin and mutual-best features
France distribution shiftNeutral features, monotone constraints, multilingual models, leave-one-country-out
The filter over-prunes FranceRank-based filter features next to raw scores, a leave-one-country-out check on filter recall and size, France's candidate-count distribution compared with US and India
Leakage in stacking inflates validationStrict out-of-fold for every model-derived feature
Overfitting the public leaderboardChoose by 5-fold score. Use the leaderboard for probes, not tuning.
Rejected file formatValidator in the pipeline, explicit \n line endings and UTF-8 on Windows
Running out of timeA submission at every stage, freeze at 18:00 Day 3
